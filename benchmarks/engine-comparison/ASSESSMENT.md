# Engine decision for Rocky DB

**Recommend Turso for a Rocky implementation that actually accepts concurrent, independent logical mutations in one file, using MVCC with the explicit logical-operation/outbox path as its primary write path.** The measured advantage is large enough to justify a Turso storage adapter and a focused compatibility qualification. This is a conditional foundation recommendation, not a claim that Turso wins every deployment. If the proposed implementation retains one serial writer per file, or partitions independent work across files, choose SQLite WAL instead: these runs do not demonstrate a material Turso advantage for that topology.

**Do not make full built-in CDC on every MVCC write the primary design.** On pinned Turso 0.8.1 it passes the tested correctness properties but removes the concurrent-write performance advantage under FULL/fullfsync durability. Turso WAL plus CDC is a viable managed SQL bridge with a real maintenance advantage over custom triggers; its throughput alone does not justify changing engines. Select journal mode at database initialization. MVCC explicit connections can leave CDC off; managed SQL connections must enable capture and provide framework transaction/origin metadata. The mixed-path optimization itself is not benchmarked here and must not be assumed cost-free.

## Why the measured benefits meet the predeclared threshold

The criteria were written before measuring in [CRITERIA.md](CRITERIA.md): >=25% representative committed-throughput improvement without materially worse transaction p99, or substantially simpler reliable capture integration. Three repeated warm-cache durable-disk runs and longer follow-ups support the explicit MVCC concurrency advantage. The final explicit control stores complete declared JSON operation bodies, with entity IDs and field/authority intent; it confirms the result survives a larger credible payload. Earlier matrix/focused profiles used compact symbolic markers. They are separate profiles, not combined into one mean. The following values are medians, not best runs:

| Workload | SQLite explicit tx/s | Turso MVCC explicit tx/s | Relevant result |
|---|---:|---:|---|
| Independent, 4 writers, batch 1, one file; complete JSON operations | 222 | 645 | 2.91×; p99 330.0 → 9.0 ms |
| Independent, 8 writers, batch 4, one file; short matrix | 291 | 1,215 | 4.17×; p99 596.5 → 8.5 ms |
| Incoming replication, 4 writers, batch 16; short matrix | 262 | 482 | 1.84×; remote materialization not reauthored |
| Mixed, 4 writers, batch 4, three revision observers; longer samples | 258 | 648 | 2.51× writer throughput; observer latency regresses |
| Independent, 4 writers, batch 4, four files; longer samples | 358 | 329 | No MVCC advantage once each file has one writer |
| Serial common crypto, batch 4; complete operation payload | 248 | 223 | No Turso advantage; payload and verification costs included |

Mutations/s equals tx/s times declared batch size. It counts logical ERP requests, not captured physical row records. Serial authoritative transactions and single-writer drafts are mostly persistence-bound; there is no repeatable major advantage attributable to multiwriter MVCC there. Contended writes share entity and author cursor rows; retries remain and benefits are much smaller than independent writes. All successful runs check author cursor totals, so retries are not counted as committed work and silently lost requests would fail the run.

Independent one-file benefit is specific to genuine concurrently committing transactions. Running a single writer actor on Turso will not reproduce it. SQLite partitioning changes the atomicity domain; four files answer a different question from four writers in one file. On this APFS/fullfsync setup partitioning also does not yield linear scaling: storage flushes and host effects remain shared.

## CDC is meaningful, but does not explain the explicit-path win

Full row capture preserves transaction boundaries, savepoint rollback and restartability in both adapters. Turso v0.8.1 supports CDC after MVCC is initialized, exposes CDC v2 transaction IDs and commit records, and rejects switching journal modes while capture is active. The actual pinned source and runtime checks agree; there is no blanket CDC/MVCC incompatibility.

Turso removes generation and migration of 21 SQLite capture triggers in this schema. It centralizes row capture and typed before/after production in the engine, a meaningful maintenance benefit for a managed SQL bridge. But origin metadata, safe durable consumption, retained schema knowledge, logical intent, policy, signatures and encryption remain framework work. This prototype saves a compact trigger generator, not the entire capture adapter. A major total engineering saving has **not** been demonstrated. See [INTEGRATION.md](INTEGRATION.md) for the responsibility comparison and source references.

In the short matrix, independent 4-writer FULL disk throughput was about 255 tx/s for SQLite trigger capture, 250 for Turso WAL CDC and 77 for Turso MVCC CDC. Longer decoded-image samples reproduce the poor MVCC CDC result (about 75 tx/s). The final matched-handle independent capture samples favor Turso WAL CDC throughput (296 versus 181 tx/s for triggers), but its p99 is worse (218 versus 89 ms). WAL CDC is not simply identical to custom capture: throughput, tail latency, payload format and integration work trade off differently. Serial authoritative full CDC on MVCC was about 13 tx/s, versus about 244 on Turso WAL CDC. Capture-disabled baselines and explicit controls are preserved for every matrix case. Subtracting their medians isolates the **combined** capture overhead, not just sequence contention; several small overhead estimates are negative because run-to-run variation exceeds the cost being measured.

The MVCC emitter allocates every captured change ID from an implicit sequence. Pinned sequence code documents autonomous inner transactions and serialization through the shared sqlite_sequence row. CPU and scaling regress sharply with full capture. This is measured evidence of a costly MVCC CDC path, consistent with shared sequence coordination plus repeated durability work. It does not prove that all overhead is caused by that row: image encoding, CDC commit records, log writes and internal retries are included. Internal sequence conflict counts are not exposed by this harness. Even separately labeled NORMAL sync and memory controls show CDC overhead; neither is used to claim a FULL-durability win.

## Correctness and consumption

All six capture/control configurations passed source-transaction rollback, savepoint rollback followed by commit, complete committed grouping, restart before capture consumption, durable cursor restart, replay deduplication and remote-origin exclusion. Captured before/after amounts are decoded and verified. All six passed acknowledged commit followed by SIGKILL and separate-process recovery with cursor consumption. This demonstrates process-crash recovery, not physical power-loss survival.

MVCC explicitly tested late visibility: one transaction remains open, another commits and is consumed, then the first commits and is consumed exactly once. An unsafe max-ID cursor would have skipped two earlier row records. The adapter therefore uses retained consumed transaction IDs with an atomic cursor update, never a bare MAX(change_id). That is reliable for the tested history but is **not a bounded production retention design**. Source upstream sync uses sequence_watermark_experimental; qualifying and implementing that optimized cursor, or a bounded retained-identity checkpoint protocol, remains work.

With the reserved consumer, median foreground rates were 135 tx/s for SQLite triggers, 180 for Turso WAL CDC, 31 for Turso MVCC CDC, and 628 for Turso MVCC explicit. Foreground consumed counts were respectively 400, 377, 368 and 400 out of 400 timed transactions; residual drain medians were approximately 2 ms, 285 ms, 1.37 seconds and 4 ms. This is a short-history catch-up check, not a steady-state lag guarantee.

The final matched-handle independent case retains about 10.49 MiB for SQLite triggers, 7.33 MiB for Turso WAL CDC and 0.41 MiB for Turso MVCC CDC; explicit paths retain about 4.52, 5.37 and 0.17 MiB respectively. With compact metadata, capture image payload itself is about 79,072 bytes for generated JSON staging versus 40,427 bytes for binary CDC, with different commit/metadata record counts. Complete-operation follow-ups retain 87,089 logical payload bytes; CDC also captures the txmeta payload, increasing its image bytes to 121,893 while SQLite staging remains at 79,072. Complete-operation total file snapshots are about 11.58/9.10/0.57 MiB for SQLite trigger/Turso WAL CDC/Turso MVCC CDC, versus 5.87/6.93/0.25 MiB for their explicit paths. This metadata capture duplication is a concrete integration cost of the unfiltered full CDC configuration, not hidden behind a tiny marker. MVCC logical-log size and WAL size are different representations under different default checkpoint policies; these snapshots are not evidence of long-term space amplification or a storage plateau. See [charts/storage.png](charts/storage.png).

The initial WAL consumer often failed read-to-write upgrades and did not keep up while producers wrote. A follow-up reserves the WAL writer before reading and advancing the cursor; it does make foreground progress, at a throughput cost. Those versions are preserved separately. Producer-only rates from a starved consumer must not be interpreted as sustainable end-to-end captured throughput. Residual drain rates, foreground drain counts and consumer latencies are in the raw files and summaries. Direct lag follow-ups report median run p95 commit-to-consumption lag of about 399 ms for SQLite triggers, 1,101 ms for Turso WAL CDC, 2,186 ms for MVCC CDC, 932 ms for SQLite explicit, 672 ms for Turso WAL explicit and 13 ms for MVCC explicit. These lag runs used compact markers and retained-handle/cursor instrumentation; do not assume identical lag with larger operation payloads. Up to six timings per 400 transactions are excluded when consumption completes before the producer records its acknowledgment timestamp; missing counts are retained. Long retained-history catch-up is not qualified by these short runs.

## Costs, variance and deployment limits

The longer FULL independent explicit case uses roughly 24.5 MiB peak RSS for Turso MVCC versus 12.5 MiB for SQLite; whole-process CPU per timed commit is roughly 1.4 versus 0.42 ms, including seed and drain costs. MVCC buys throughput by doing more parallel work, not by uniformly using fewer resources. Mixed-query observer p95 is about 8.2 ms on MVCC explicit versus 0.17 ms on SQLite explicit. This may be acceptable for UI invalidation, but a strict low-latency query budget could reverse the engine choice. MVCC full CDC mixed peak RSS reaches about 111 MiB in this small scenario.

The serial in-memory control favors SQLite; it has no disk persistence and cannot run SQLite WAL, so it is not evidence against the durable concurrent MVCC result. NORMAL disk results are weaker durability and are explicitly separate. All main disk measurements fit in the page cache after seeding and warm-up. No cold-cache, sustained multi-hour retention, mobile battery, Android/iOS, physical power-cut, cross-process writer or large-index test is claimed.

CPU/RSS include initialization and residual drain. Latency includes contention retries. Short-matrix p99 has only 40 samples per writer; longer runs have 100. There are three repeats, rotating engine order, on an otherwise uncontrolled laptop. Averages of the p99 percentiles are not used: tables report median run percentiles with min/max available in summary.csv. WAL/checkpoint and MVCC GC defaults differ. Early storage samples closed SQLite's final connection before sampling, so they are labeled as lifecycle-biased; retained-handle follow-ups are the valid cross-engine storage comparison. These caveats bound the result rather than erase large repeated differences.

The existing p2panda SQLite store is a useful starting point, but sharing application projections and the canonical signed outbox in its transaction still needs work. Turso requires a new store adapter plus compatibility tests for Rocky's actual SQL, migration, observable-query and SDK/platform surface. These operational costs are justified **when the measured independent one-file concurrency is a real bottleneck**. For a serial-authority or partitioned first PoC, they have no demonstrated performance payoff and built-in CDC alone has not shown a sufficiently large total integration saving here.

Choose by topology:

- **Turso MVCC + explicit operations:** independent concurrent local edits, incoming independent projection batches, and mixed writes with an observer budget around the measured millisecond range.
- **Turso WAL + CDC:** managed SQL capture where engine-owned before/after and transaction grouping are valuable; qualify cursor/retention and accept one writer per file.
- **SQLite WAL + generated capture or explicit operations:** serial authoritative groups, one managed writer per file, independent partitions, tight reader/CPU/memory budgets, or workloads dominated by serial in-memory execution.
- **Insufficient evidence:** deciding from long-lived capture history, mobile/platform support, cold storage, physical power-loss behavior, or an unknown real workload mix. Those are not settled by this benchmark.

This is local engine evidence. It does not measure P2P scalability, conflict semantics, Raft throughput over the network, signatures/encryption in the full p2panda stack, or a completed Rocky framework.
